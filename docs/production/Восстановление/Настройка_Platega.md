# Stage 8 — Platega, общая платёжная страница

> Историческая инструкция Stage 8 и результаты тестового контура 23.09.2026. Упомянутые старые каталоги /root/Stage8-Deployment, контейнеры отката и подтверждения тестов не являются текущим комплектом восстановления. Не выполняйте исторические команды как актуальную процедуру.

Текущие процедуры: [подключение и сверка Platega](../README/13_Подключить_реальную_оплату_Platega.md), [диагностика env](../README/34_check_env.md), [восстановление](00_Состав_и_порядок.md). Текущий preflight исключает семь устаревших SELLER-полей; новые продажи контролирует также checkoutEnabled в БД. Аутентифицированные callback/GET остаются возможными после закрытия новых покупок. Ниже сохранён исторический материал с его исходными датами.

Версия рабочего комплекта: `Prod-1.1`. Ниже сохранены пояснения по истории платёжного модуля и ранее выполненным тестам.

## Заполнить после получения ключей

Основной файл сервера: `/opt/gspro/.env`. Блок Platega находится в начале файла.
Код с пояснениями параметров: `/opt/gspro/app/lib/platega-config.js`, в самом начале.
Шаблон без секретов: `/opt/gspro/app/.env.example`, в самом начале.

```dotenv
# CHANGEABLE — НАСТРОЙКИ PLATEGA
PLATEGA_ENABLED=false
PLATEGA_MERCHANT_ID=
PLATEGA_SECRET=
```

В `PLATEGA_MERCHANT_ID` вписать MerchantId, в `PLATEGA_SECRET` — API-ключ, выданные менеджером или кабинетом Platega. Значения не публиковать и не помещать в JavaScript браузера. Файл `.env` должен оставаться с правами 600. `.env.runtime` формируется автоматически через `deploy/dc`, его вручную не редактировать. Настоящие ключи не нужно вставлять в `platega-config.js`: этот файл читает закрытые переменные окружения.

В кабинете Platega, «Настройки → Callback URLs», указать:

`https://gspro.store/api/payments/platega/callback`

При другом домене заменить домен и проверить `DOMAIN` в `.env`. `NEXT_PUBLIC_SITE_URL` задаётся Docker Compose как `https://${DOMAIN}`. После смены домена требуется пересборка web. Адреса возврата формируются автоматически: `/order/success?order=НОМЕР`, при неуспехе добавляется `&payment=failed`. Номер заказа или параметр URL не подтверждают оплату.

У менеджера подтвердить доступность общей платёжной страницы `/v2/transaction/process` и требования к метаданным. GSPro передаёт `metadata.userId` — внутренний идентификатор зарегистрированного покупателя. Игровые логины, пароли, UID и email в запрос оплаты не передаются. Способ оплаты покупатель выбирает на Platega. Старые `PLATEGA_PAYMENT_METHOD`, `PLATEGA_API_MODE`, `PLATEGA_*_PATH`, `PLATEGA_BASE_URL` и HMAC-поля больше не используются. Аутентификация callback соответствует документации: `X-MerchantId` и `X-Secret` по HTTPS.

## Включение

1. Заполнить оба ключа, callback в кабинете и подтвердить доступные способы оплаты.
2. В `/opt/gspro/.env` установить `PLATEGA_ENABLED=true` и `DEPLOY_MODE=production`.
3. Выполнить предварительную проверку без переключения работающего web:

```bash
cd /opt/gspro
./deploy/dc run --rm --no-deps --entrypoint node web scripts/preflight.mjs
```

Существующая production-проверка требует также заполненных реквизитов и подтверждённых бизнес-настроек. При ошибке исправить названные параметры; не подставлять формальные подтверждения без проверки. До успешной проверки действующий контейнер продолжает работать со старым окружением. Не переключать его с ошибочным env.

4. После успешной проверки применить окружение:

```bash
./deploy/dc up -d --no-deps --force-recreate --wait web
systemctl enable --now gspro-platega-reconcile.timer
curl -fsS https://gspro.store/api/health
```

После применения окружения владелец отдельно открывает в веб-админке раздел приёма оплаты и включает `TechnicalSettings.checkoutEnabled` в БД. Это поле имеет приоритет над прежним `PLATEGA_ENABLED`; без него текущая инструкция по одному `.env` не включает новые платежи. Проверьте ответ `/api/admin/payment-availability` под учётной записью с правом на этот раздел и реальный контрольный заказ. При отсутствии ключей или выключенном поле БД платные заказы не создаются. Промокод на 100% не требует платёжной операции.

5. Выполнить один согласованный контрольный платёж: проверить переход в Platega, сумму, callback, статус «В работе» в кабинете, событие в Telegram и ручное выполнение оператором. Без MerchantId/API-ключа такой внешний тест не выполнен. Если кабинет менеджера предоставляет тестовый режим, сначала использовать его по его инструкции; выдуманного sandbox-адреса в коде нет.

## Логика заказа

Сумма берётся из сохранённого заказа на сервере. Перед обращением к API сохраняется `PaymentAttempt`: попытка, сумма, валюта, связь с заказом. Идентификатор попытки передаётся в `payload`. После ответа сохраняются UUID транзакции и ссылка на `https://pay.platega.io`.

Повторное нажатие возвращает ту же активную ссылку. Одновременные запросы синхронизированы блокировкой PostgreSQL. Недокументированная идемпотентность Platega не предполагается; автоматических повторов POST после таймаута нет.

Подтверждение `CONFIRMED` проверяет идентификатор, точную сумму в копейках и валюту. В одной транзакции меняется заказ и фиксируется обработанное событие. Статус становится `FULFILLING` («В работе»), записывается `paidAt`; существующий триггер создаёт `TelegramEvent`, который обрабатывает бот. Автоматического пополнения игры нет. Сохраняется существующее уведомление покупателя по email; его доставка не является условием подтверждения оплаты.

`CANCELED` завершает попытку, но не откатывает уже подтверждённую оплату. После отмены попытки можно повторить оплату, пока не истёк срок заказа. Локальный таймер сам по себе не доказывает отмену платежа в Platega. `CHARGEBACKED`, двойная оплата или оплата уже отменённого заказа переводят заказ в `REFUND_PENDING` для разбора оператором; код сам не делает возврат денег и не запускает выполнение.

Страница возврата запрашивает статус только авторизованного владельца заказа. Произвольный `?free=1` или `?demo=1` больше не показывает ложное подтверждение. В кабинете доступны «Оплатить через Platega» и «Проверить оплату».

## Пропущенный callback и неопределённый ответ

Таймер `gspro-platega-reconcile.timer` каждые две минуты проверяет известные незавершённые транзакции через `GET /transaction/{id}`. Доступен и ручной запуск:

```bash
systemctl start gspro-platega-reconcile.service
journalctl -u gspro-platega-reconcile.service -n 30 --no-pager
```

Таймаут создания или потеря ответа оставляет попытку `UNKNOWN` (либо `CREATING` при падении процесса). Новая попытка заблокирована. Если callback придёт первым, сервер найдёт связь по `payload` через авторизованный GET. Если callback не пришёл и UUID неизвестен, оператор находит транзакцию в кабинете Platega по заказу/описанию и проверяет её вручную:

```bash
cd /opt/gspro
./deploy/dc exec -T web node scripts/platega-reconcile.mjs UUID_ТРАНЗАКЦИИ
```

Скрипт сам запросит Platega, проверит сумму/валюту/payload и сохранит результат. Не редактировать сумму или статус заказа вручную ради обхода неизвестной попытки. Если транзакция не найдена, сначала подтвердить отсутствие платежа у Platega; автоматической кнопки сброса нет. При 404/ошибках API платёж не считается отменённым.

## Резервирование, перенос, откат

Миграция Stage 8 только добавляет `PaymentAttempt` и переносит в неё существующие настоящие UUID транзакций. Данные заказов не удаляются. PostgreSQL dump Stage 8 автоматически включает новую таблицу.

Перед выпуском создаётся согласованный pre-release архив по регламенту Stage 8. Дополнительно сохраняются предыдущие env и Dockerfile в `/root/Stage8-Deployment/rollback`; предыдущие образы удерживаются отдельными остановленными контейнерами. Точный архив указан в отчёте выпуска.

После восстановления архива до включения продаж сверить платежи за период после снимка с кабинетом Platega. Откат БД не отменяет банковские операции. Старые callback могут потребовать ручной привязки, если соответствующая попытка отсутствует в восстановленной БД.

При переносе используйте актуальный комплект `/root/Stage8-Deployment`. Скрипт восстанавливает `gspro-backup*` и `gspro-platega-reconcile.*` units. Таймер сверки платежей включается после переключения публичных сервисов. Инструкция Stage 8 входит в `app/docs` архивируемых исходников.

Откат к сохранённым образам и env допускается только после остановки приёма новых оплат и сверки появившихся транзакций. Новую таблицу при откате не удалять. Для полного восстановления использовать `/root/Stage8-Deployment/README-Deployment.md`.

В авторизации указан https://app.platega.io; официальный SDK также использует только этот адрес. Упоминание Demo Merchant в примере ответа и поля x-apidog-mock в примере подписки не документируют отдельную платёжную среду без денежных операций. Кнопка запуска запроса в Apidog не означает, что транзакция не будет реальной.

Это вывод о публичной документации, а не утверждение об отсутствии закрытого режима у провайдера. На сайте Platega встречается выражение «тестовые операции», но не уточняется отсутствие реального списания.

Для менеджера подготовлен точный вопрос:
«Нужен тестовый контур для общей платёжной страницы POST /v2/transaction/process без реального движения денег. Предоставляете ли вы sandbox или тестовый merchant? Нужны API base URL, MerchantId/Secret, инструкция подтверждения/отмены тестового платежа и настройки callback. Подтвердите, что в этом режиме нет реальных списаний и комиссий».

Сообщение менеджеру автоматически не отправлялось.

## Наш тестовый контур GSPro

Он уже создан и использован для Stage 8:
- отдельный контейнер PostgreSQL gspro-stage8-db с вымышленными заказами;
- отдельная Docker-сеть gspro-stage8-test с internal=true;
- тестовые учётные данные, не связанные с магазином Platega;
- имитация ответов провайдера в тестах с реальными операциями нашей тестовой БД;
- HTTP-проверки настоящих обработчиков GSPro с тестовыми callback;
- отсутствие настоящего Telegram-бота и настроенного SMTP в тестовой базе.

Тесты проверяют backend и наши сценарии. Они не подтверждают доступность методов для вашего магазина, реальные комиссии, поведение банков и фактическую доставку callback от инфраструктуры Platega.

Повторные backend-проверки проводите на отдельном тестовом сервере с изолированной БД и тестовыми настройками. Рабочую БД и реальные внешние отправки в тестах не используйте.

Для собственных тестов ключи от менеджера не нужны. Проверка через инфраструктуру самой Platega требует предоставленного ею доступа и подтверждённых правил тестового режима.


## Stage8.1: данные заказа и завершение

После оплаты идентификатор транзакции Platega виден в заказе покупателя, основной админке и Mini App. При статусе «Выполнен» пароль удаляется из рабочей базы, включая смену статуса через Telegram; логин и UID остаются. Отмена статуса пароль не восстанавливает. В админках показывается предупреждение. Старые зашифрованные резервные копии сохраняют прежнее содержимое до ротации; очистка после восстановления описана в README-Deployment.md.

## Быстро вернуться в no-production

После включения production отключить создание новых реальных платежей одной командой:

```bash
sudo bash /opt/gspro/deploy/disable-payments.sh
```

Обновлённый скрипт сначала устанавливает `TechnicalSettings.checkoutEnabled=false` в БД, затем `DEPLOY_MODE=no-production` и `PLATEGA_ENABLED=false`, пересоздаёт web и Mini App и проверяет значения. Пользователи, заказы и ключи сохраняются; версия кода не откатывается. Перед вызовом проверьте, что на сервере установлена обновлённая версия скрипта.

Ранее выданные ссылки Platega не отменяются автоматически. Подписанный callback по уже существующему заказу может быть обработан после отключения новых покупок: незавершённые оплаты нужно отдельно проверить у провайдера. Применяются все текущие изменения env. После переключения: `sudo bash /opt/gspro/deploy/start-and-check.sh --check-only`. Production-preflight при выключенных платежах ожидаемо не проходит.


Актуальные варианты релиза: production-1.1 и no-production-1.1. RELEASE_VERSION и APP_TAG содержат полное имя версии; DEPLOY_MODE содержит production или no-production. Команда отключения устанавливает no-production-1.1 и не выводит исторические имена контейнеров. Политика env автоматически удаляет семь исключённых полей SELLER из действующих файлов и шаблонов. Подробнее: docs/RELEASES_1.1.md в исходниках.
