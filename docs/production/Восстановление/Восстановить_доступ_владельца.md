# Ручное восстановление владельца через VPS

Редакция: **28.09.2026**.

Это инструкция для системного администратора, имеющего независимый доступ к VPS по SSH или через консоль хостинга. Она не создаёт скрытой страницы, API обхода авторизации или универсального пароля.

Не хранить здесь реальные пароли, ключи SSH, секреты TOTP, QR-коды или резервные коды. Проверьте полномочия человека, для которого восстанавливается доступ. Обычным сотрудникам доступ к VPS не выдавать.

## Сначала определить причину

- Забыт пароль, почта доступна: штатное восстановление на сайте. При включённой 2FA нужен также код приложения или одноразовый резервный код.
- Потеряно приложение, резервные коды есть: вход/восстановление с резервным кодом; затем переподключение 2FA из профиля.
- Потеряны все вторые факторы или роль владельца: ручное действие через VPS, описанное ниже.
- Возможен захват почты, Telegram или VPS: сначала восстановить контроль над соответствующим каналом. Не отправлять восстановление на скомпрометированную почту.

## Порядок

1. Войти на сервер своим SSH-ключом или через защищённую консоль хостинга. Сделать штатную резервную копию, согласовать короткое окно обслуживания.
2. Сверить версию (`cat /opt/gspro/VERSION`) и наличие таблиц `StaffAccess`, `AccountSecurity`. Для старого снимка инструкция может не подходить; не выполнять SQL вслепую.
3. При подозрении на захват завершить доступ приложений на время работ: `cd /opt/gspro && deploy/dc stop web telegram-admin telegram-bot`. Это временно делает сайт недоступным, база продолжает работать.
4. Открыть PostgreSQL: `docker exec -it gspro-stage5-vps-db-1 psql -U gspro -d gspro`. Имя контейнера сверить через `deploy/dc ps db`.
5. В интерактивном psql указать email нужного существующего аккаунта и проверить единственную запись. Email в примере — заглушка, его заменить.

```sql
\set owner_email 'replace-with-owner-email@example.invalid'
SELECT id,email,role,"deletedAt","deletionRequestedAt"
FROM "User" WHERE email=:'owner_email';
```

Не продолжать, если запись не найдена, удалена, ошибочно выбрана или есть сомнение в принадлежности. Скопировать её точный `id` в переменную psql:

```sql
\set owner_id 'REPLACE_WITH_VERIFIED_USER_ID'
BEGIN;
SELECT pg_advisory_xact_lock(8223001);
SELECT id,email,role FROM "User" WHERE id=:'owner_id' FOR UPDATE;
UPDATE "User" SET role='SUPER_ADMIN',"sessionVersion"="sessionVersion"+1
WHERE id=:'owner_id' AND "deletedAt" IS NULL AND "deletionRequestedAt" IS NULL;
INSERT INTO "StaffAccess" ("userId",enabled,web,mini,bot,"acceptedAt","updatedAt")
SELECT id,true,true,false,false,CURRENT_TIMESTAMP,CURRENT_TIMESTAMP
FROM "User" WHERE id=:'owner_id' AND role='SUPER_ADMIN'
ON CONFLICT ("userId") DO UPDATE SET enabled=true,web=true,"acceptedAt"=CURRENT_TIMESTAMP,"updatedAt"=CURRENT_TIMESTAMP;
DELETE FROM "AuthSession" WHERE "userId"=:'owner_id';
DELETE FROM "PasswordReset" WHERE "userId"=:'owner_id';
DELETE FROM "SecurityEmailChallenge" WHERE "userId"=:'owner_id';
INSERT INTO "SecurityAudit" (id,"userId",action,"createdAt")
VALUES (gen_random_uuid()::text,:'owner_id','OWNER_MANUAL_RECOVERY',CURRENT_TIMESTAMP);
```

6. **Только если утрачены приложение и резервные коды**, в этой же транзакции снять 2FA именно у проверенного аккаунта:

```sql
UPDATE "AccountSecurity" SET "secretEncrypted"=NULL,"enabledAt"=NULL,
"pendingEncrypted"=NULL,"pendingExpiresAt"=NULL,"pendingSessionId"=NULL,
"backupHashes"=ARRAY[]::TEXT[],"lastStep"=-1,failures=0,"lockedUntil"=NULL
WHERE "userId"=:'owner_id';
INSERT INTO "SecurityAudit" (id,"userId",action,"createdAt")
VALUES (gen_random_uuid()::text,:'owner_id','TWO_FACTOR_MANUAL_RESET',CURRENT_TIMESTAMP);
```

При подозрении на захват Telegram отдельно убрать привязку и запретить Telegram-каналы:

```sql
UPDATE "StaffAccess" SET mini=false,bot=false,"telegramId"=NULL,
"pendingTelegramId"=NULL,"linkHash"=NULL,"linkExpiresAt"=NULL,"updatedAt"=CURRENT_TIMESTAMP
WHERE "userId"=:'owner_id';
```

7. Сверить результат до сохранения. При ошибке — `ROLLBACK;`, при верном результате — `COMMIT;`. Не записывать новый пароль в SQL: при необходимости сменить его через штатное почтовое восстановление после возврата сайта.
8. Если сервисы останавливались: `cd /opt/gspro && deploy/dc up -d --no-build --wait web telegram-admin telegram-bot`. Проверить здоровье сервисов и вход владельца. Сразу заново настроить 2FA и сохранить новые резервные коды. При необходимости заново подтвердить Telegram.
9. Зафиксировать время, причину и исполнителя работ в административном журнале без секретов.

## После восстановления старого бэкапа

До открытия админки сверить актуальные роли, отозванных сотрудников, Telegram-привязки и состояние 2FA. Старый снимок может вернуть прежние права или использованные резервные коды; при необходимости перевыпустить коды и завершить все старые сессии. Установщик deploy-new-vps.sh выполняет очистку завершённых игровых паролей через scripts/purge-completed-passwords.mjs до открытия сервисов.

Старые файлы `operators.txt`, `admins.json` и скрипты их редактирования не являются источником действующих прав.
