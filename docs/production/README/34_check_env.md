# Диагностика .env установленного GSPro

Из проверок и отчёта о неприменённых переменных исключены `SELLER_INN`, `SELLER_POSTAL_ADDRESS`, `SELLER_OGRN`, `SELLER_PHONE`, `SELLER_TYPE`, `SELLER_NAME`, `SELLER_LEGAL_ADDRESS`. Их отсутствие, формат и заглушки не блокируют обычный или подробный preflight. `SELLER_EMAIL` продолжает проверяться. Политика env удаляет эти семь устаревших полей из env-файлов при deploy/dc; не рассчитывайте сохранить их в .env. Юридические тексты и сведения о продавце нужно проверять в действующем контенте и настройках приложения отдельно.

На установленном VPS:

```bash
sudo bash /opt/gspro/deploy/check-env.sh
```

1. **Файлы и инструменты:** наличие .env, Compose и скриптов; повторяющиеся переменные с номерами строк.
2. **Свежая конфигурация:** `deploy/dc` обновляет `.env.runtime` и формирует настройки Compose. Значения и исходный stderr не печатаются: ошибки интерполяции могут содержать секреты.
3. **Подробный preflight:** временный контейнер получает новое окружение и подробный проверочный JS через read-only mount с сервера. Поэтому пересобирать приложение для запуска этой диагностики не требуется. Проверяются обязательные поля, ключи, реквизиты, флаги, наличие настроек Platega и лимиты. Ошибки содержат имена переменных, но не значения. Фильтр заглушек соответствует штатному preflight и может сработать даже на строке ключа; это не повод произвольно менять ключи существующих данных.
4. **База:** ещё один временный контейнер выполняет только `SELECT 1` с новым окружением. Операция проверяет фактическое подключение к PostgreSQL, без изменения данных.
5. **Применение:** новые настроенные переменные сравниваются с окружением существующих web, Mini App и бота. `НЕ ПРИМЕНЕНО` перечисляет имена отличающихся переменных.

Код выхода **0** — проверки прошли и настроенные переменные совпадают; **1** — ошибки с указанием этапов; **2** — ошибок проверки нет, но новое окружение ещё не применено. Скрипт не запускает основной сайт, не пересоздаёт работающие контейнеры, не применяет миграции и не создаёт платежи. Временные контейнеры удаляются после завершения. Рабочие образы должны уже существовать на сервере. Нужны Bash, Python 3, Docker Compose.

## Когда применяется .env

Сохранение `.env` не изменяет окружение уже созданного контейнера. Следующий вызов `deploy/dc` перечитывает файл и обновляет `.env.runtime`. Команда `deploy/dc run ...` создаёт отдельный контейнер с новыми значениями. Команда `deploy/dc exec ...` работает со старым окружением существующего контейнера.

Обычные `docker restart` и `deploy/dc restart` не перечитывают новые переменные. После исправления ошибок и проверки можно применить настройки сайта:

```bash
cd /opt/gspro
./deploy/dc up -d --no-deps --no-build --force-recreate --wait web
sudo bash deploy/check-env.sh
sudo bash deploy/start-and-check.sh --check-only
```

Пересоздание web на короткое время прерывает его обслуживание. При изменении настроек Mini App/бота аналогично пересоздайте только соответствующие сервисы `telegram-admin`/`telegram-bot` после проверки. Скрипт диагностики не делает этого автоматически. Не пересоздавайте db ради изменения реквизитов или Platega. Изменение пароля в .env само по себе не меняет пароль роли PostgreSQL; ключи шифрования существующих данных нельзя заменять без миграции.

Поля `NEXT_PUBLIC_*`, встроенные в браузерную сборку (например, смена домена), могут требовать пересборки образов. Для серверных ключей Platega и реквизитов достаточно корректного нового окружения и пересоздания соответствующего сервиса.

Прохождение диагностики подтверждает конфигурацию и доступ к БД, но не действительность Merchant ID/API-ключа у Platega, доставку callback, фискализацию или реальную оплату. Новые подтверждающие флаги не включаются скриптом.

## Включить или закрыть новые продажи

В админке используйте «Приём платежей на сайте». Значение `TechnicalSettings.checkoutEnabled` хранится в БД и входит в полный дамп. Изменение требует права `checkout.write`, подтверждения 2FA и записывается в аудит.

Текущий комплект один: сохраняйте `DEPLOY_MODE=production`, ключи Platega и корректный HTTPS-адрес. Галочка не требует пересборки, другого набора образов или пересоздания контейнеров. `PLATEGA_ENABLED` служит исходным значением только до задания настройки в БД; явная настройка БД имеет приоритет.

Выключение блокирует новые платные заказы и создание ссылок. Проверка уже начатых платежей и аутентифицированные callback продолжаются. Выданные ссылки у Platega автоматически не отменяются; разберите незавершённые операции и сверяйте их отдельно. Заказ с полной скидкой по промокоду может пройти без оплаты.

После переключения проверьте значение галочки и соответствующий пользовательский сценарий. Диагностика env не заменяет проверку настройки БД, доступов, реальной оплаты и доставки callback.

Редакция: **28.09.2026**. Диагностика на VPS в этой актуализации не запускалась. `check-env.sh` не пересоздаёт работающие контейнеры, но `deploy/dc` обновляет `.env.runtime` и применяет политику окружения. Не запускайте диагностику одновременно с несогласованной правкой env.
