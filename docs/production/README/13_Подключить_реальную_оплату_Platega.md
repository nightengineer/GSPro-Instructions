# Подключить реальную оплату Platega

Редакция: **28.09.2026**. Инструкция описывает текущую реализацию GSPro по снимку исходников и актуальному комплекту восстановления. Основная папка: `/opt/gspro`; команды выполняются на VPS по SSH. Настройки мерчанта меняет его владелец. Реальные платежи, доступность внешнего API и доставка callback в этой актуализации не проверялись.

## 1. Какой URL вставить в кабинете Platega

Откройте `https://my.platega.io`, выберите магазин **GSPRO.Store**, затем настройки (шестерёнка). Найдите **Callback URL — Адрес для POST-уведомлений**. В поле **URL** вставьте целиком, без кавычек, пробелов и завершающего слеша:

```text
https://gspro.store/api/payments/platega/callback
```

Нажмите **«Сохранить изменения»**, заново откройте настройки и убедитесь, что URL сохранился именно у нужного магазина. В документации провайдера раздел называется «Настройки → Callback URLs»; на предоставленном снимке поле называется «Callback URL».

Это адрес входящих уведомлений об оплате. Не вставляйте сюда адрес главной страницы, `/order/success`, адрес Platega, localhost или IP контейнера. Ключи и номер заказа в URL не добавляются. Изменение только этого поля не требует перезапуска GSPro.

По требованиям Platega endpoint должен быть публичным HTTPS-адресом с доверенным TLS-сертификатом, принимать POST с JSON и успешно отвечать HTTP 200. При отсутствии успешного ответа провайдер указывает таймаут 60 секунд и до трёх повторов с интервалом пять минут. Сохранение URL сейчас не гарантирует повторную доставку старого платежа: для него используйте сверку из раздела 7. [Документация callback](https://docs.platega.io/callback-об-изменении-статуса-транзакции-29209725e0).

## 2. Соответствие полей кабинета и настроек GSPro

| Что в Platega | Где в GSPro | Что именно вводить |
|---|---|---|
| ID выбранного магазина / MerchantId | `/opt/gspro/.env`, `PLATEGA_MERCHANT_ID` | Полный ID, а не сокращение вида `57ac23...7b0e` |
| API-ключ / Secret этого магазина | `/opt/gspro/.env`, `PLATEGA_SECRET` | Полный действующий секрет, без маски и многоточий |
| Callback URL | Поле URL в кабинете Platega | `https://gspro.store/api/payments/platega/callback` |
| Домен сайта | `/opt/gspro/.env`, `DOMAIN` | `gspro.store`, без `https://` и пути |
| Исходное значение приёма платежей до задания настройки БД | `/opt/gspro/.env`, `PLATEGA_ENABLED` | `true` для настроенного production; явная настройка БД имеет приоритет |
| Приём новых платных заказов | Админка → «Приём платежей на сайте» | Галочка `TechnicalSettings.checkoutEnabled`; право `checkout.write` и 2FA |
| Режим работы сайта | `/opt/gspro/.env`, `DEPLOY_MODE` | `production` |

На предоставленном снимке Platega предупреждает: полный ключ доступен для копирования только сразу после перевыпуска. Если рабочий ключ уже сохранён на сервере, не нажимайте «Сгенерировать» просто для проверки. При согласованной ротации сохраните новый ключ в защищённом хранилище, сразу замените `PLATEGA_SECRET` на VPS и примените окружение. Рассинхронизация ключа нарушает API-запросы и проверку callback.

Настройки добавляются в существующий `.env`; не заменяйте весь файл этим фрагментом:

```dotenv
DOMAIN=gspro.store
PLATEGA_MERCHANT_ID=ПОЛНЫЙ_ID_ИЗ_КАБИНЕТА
PLATEGA_SECRET=ПОЛНЫЙ_API_КЛЮЧ_ИЗ_КАБИНЕТА
PLATEGA_ENABLED=true
DEPLOY_MODE=production
```

Секреты не вставляются в исходники, URL, сообщения, скриншоты или переменные `NEXT_PUBLIC_*`. `.env` хранится с правами 600. `.env.runtime` формируется обёрткой `deploy/dc`, вручную его не правят. Действующий VPS использует также `.env.telegram` и compose-файлы web/Mini App: применяйте `deploy/dc`, а не произвольный `docker compose` без этих файлов.

`NEXT_PUBLIC_SITE_URL` задаётся Compose как `https://${DOMAIN}`. Полей `PLATEGA_CALLBACK_URL`, отдельного callback secret и HMAC-подписи в текущем коде нет. `PLATEGA_BASE_URL`, `PLATEGA_API_MODE`, `PLATEGA_PAYMENT_METHOD` и `PLATEGA_*_PATH` не используются. URL API и пути заданы в `app/lib/platega-config.js` и `app/lib/platega.js`.

## 3. Все каналы связи

| Направление | Адрес / механизм | Назначение |
|---|---|---|
| GSPro → Platega | `POST https://app.platega.io/v2/transaction/process` | Создать платёжную ссылку |
| Браузер покупателя → Platega | Полученная ссылка на `https://pay.platega.io` | Выбрать способ и оплатить |
| Platega → GSPro | `POST https://gspro.store/api/payments/platega/callback` | Передать статус транзакции |
| GSPro → Platega | `GET https://app.platega.io/transaction/{UUID}` | Проверить уже созданную транзакцию |
| Браузер → GSPro | `https://gspro.store/order/success?order=НОМЕР` | Возврат после платёжной формы |
| Браузер → GSPro при неуспехе | Тот же URL с `&payment=failed` | Показать результат возврата |

GSPro отправляет API-запросы с `Content-Type: application/json`, `X-MerchantId` и `X-Secret`; callback проверяется по тем же двум заголовкам и текущим значениям сервера. Авторизация покупателя/CSRF нужна для его действий на сайте, но callback не требует пользовательской сессии.

В запрос создания входят: сохранённая сумма заказа в рублях (`paymentDetails.amount`), валюта (`currency`), описание с номером заказа (`description`), адреса возврата (`return`, `failedUrl`), ID попытки оплаты (`payload`), внутренний ID покупателя (`metadata.userId`). Игровые пароли, UID, логин и email этот модуль в запрос Platega не передаёт. `paymentMethod` не задаётся: используется общая платёжная страница. У менеджера Platega уточняются доступность метода и требования к метаданным конкретного мерчанта. [Создание платежа](https://docs.platega.io/создание-платежной-ссылки-без-заданного-метода-33845703e0).

Ответ создания должен содержать UUID `transactionId`, `status=PENDING` и HTTPS `url` на разрешённом хосте `pay.platega.io`. Они сохраняются в `PaymentAttempt` и заказе. Таймаут обращения к API — 15 секунд; редиректы API запрещены. Неопределённый результат создания не повторяется автоматически, чтобы не создавать ещё один платёж.

Адреса возврата формируются автоматически для каждого заказа: вручную в Callback URL они не вводятся. Возврат браузера, квитанция на экране или параметр `payment=failed` сами по себе не меняют подтверждённый финансовый статус.

## 4. Сеть и обработка callback

Для входящих уведомлений домен должен указывать на VPS; HTTPS/443 и сертификат должны работать. Caddy направляет этот путь в `web:3000`, а не в Mini App. Между Platega и обработчиком не должно быть страницы авторизации, CAPTCHA, блокировки POST, удаления заголовков `X-MerchantId`/`X-Secret` или перенаправления на другой домен. Используйте основной домен без `www`, чтобы избежать редиректа.

Для исходящих запросов контейнеру web нужны DNS и HTTPS-доступ к `app.platega.io:443`. Работа входящего callback не доказывает доступность исходящего API, и наоборот. Системные сетевые настройки меняются только по отдельному разрешению администратора.

Текущий обработчик ожидает поля JSON `id`, `amount`, `currency`, `status`; `paymentMethod` для обработки не нужен. `id` — UUID транзакции, сумма положительная, не более двух знаков после запятой, валюта из трёх заглавных букв. Пример структуры, **не команда для отправки в рабочий магазин**:

```json
{"id":"00000000-0000-0000-0000-000000000000","amount":1,"currency":"RUB","status":"CONFIRMED"}
```

После аутентификации callback служит сигналом для серверного GET этой транзакции. Фактический статус, сумма, комиссия, MerchantId и payload берутся только из ответа API. Код требует совпадения мерчанта, UUID, payload попытки и валюты. Подделать статус или комиссию полями callback нельзя. Если callback сообщает о подтверждении/возврате раньше, чем обновился GET, сервер отвечает 503 для повторной доставки; более старое уведомление не откатывает новый подтверждённый статус. Успешная обработка или уже обработанный дубль возвращает HTTP 200 с `ok:true`. Повторное событие не запускает повторное выполнение. В случае callback раньше ответа создания связь восстанавливается через GET Platega и `payload`.

| Ответ GSPro на callback | Значение / действие |
|---|---|
| 200, `ok:true` | Событие обработано или распознано как дубль |
| 401, `unauthorized` | Ключи отсутствуют либо заголовки не совпали; сверить магазин, актуальный секрет и окружение |
| 400, `invalid_event` | JSON, UUID, статус, сумма или валюта не соответствуют ожидаемому формату |
| 400, `invalid_payment` | Транзакция/сумма/валюта не прошли проверку связи с заказом |
| 413, `too_large` | Тело превышает 16 КиБ по проверке обработчика |
| 503, `retry_later` | Не удалось применить событие: проверить БД, привязку попытки и исходящий API |
| 404/405/301/308/502 | Проверить URL, метод POST, маршрутизацию, редиректы и доступность web |

Для безопасной проверки маршрута администратор может выполнить запрос **без ключей**, который не подтверждает оплату:

```bash
curl -sS --max-time 20 -i -X POST \
  https://gspro.store/api/payments/platega/callback \
  -H 'Content-Type: application/json' --data '{}'
```

Ожидается **401 unauthorized**. Это проверяет доступность обработчика, но не доставку от Platega и не соответствие секретов. Открытие URL в браузере отправляет GET и может вернуть 405 — это не проверка callback. Не отправляйте выдуманный `CONFIRMED` с настоящими ключами для «починки» заказа.

## 5. Применить настройки сервера

Если менялся только Callback URL в кабинете, этот раздел пропускается. Если менялись серверные ключи или другие env-настройки, выполните следующие шаги. Для изменения одной галочки приёма платежей этот раздел не нужен:

1. Уточнить условия мерчанта, способы оплаты, лимиты/комиссии и подтверждённые бизнес-настройки. Preflight не подтверждает доступ к API и не заменяет реальную проверку оплаты.
2. Отредактировать `/opt/gspro/.env` и выполнить предварительную проверку:

```bash
cd /opt/gspro
./deploy/dc run --rm --no-deps --entrypoint node web scripts/preflight.mjs
```

При ошибке исправьте названные параметры. Не устанавливайте фиктивные подтверждения. Существующий preflight проверяет в том числе `DATA_RESIDENCY_CONFIRMED`, `LEGAL_TEXTS_APPROVED`, `PAYMENT_FISCALIZATION_CONFIGURED`, `PROCESSOR_AGREEMENTS_CONFIRMED` и другие настройки приложения.

3. После успешной проверки применить env к web и Mini App:

```bash
./deploy/dc up -d --no-deps --no-build --pull never --force-recreate --wait web telegram-admin
./deploy/dc exec -T web node scripts/preflight.mjs
curl -fsS https://gspro.store/api/health
```

Обычный `restart` не подхватывает заменённое окружение. При смене домена требуется также пересборка web/Mini App с новым публичным URL и согласованное применение конфигурации Caddy; выполняйте регламент `03_Изменить_домен_и_HTTPS.md`. Замените Callback URL в Platega на новый основной домен.

`checks.payment=configured` означает только включённый модуль с непустыми ключами. Это не проверка правильности ключей, доступности API или успешно полученного callback. Секреты не проверяйте выводом `cat .env`, `printenv` или полного `docker inspect` в общий журнал.

## 6. Заказ после оплаты

| Статус Platega | Поведение GSPro |
|---|---|
| `PENDING` | Ожидание, выполнение не запускается |
| `CONFIRMED` | Для обычного ожидающего заказа: `paidAt` и `FULFILLING` («В работе») |
| `CANCELED` | Попытка отменена; уже подтверждённая оплата не откатывается |
| `CHARGEBACKED` | `REFUND_PENDING`, требуется разбор оператором |

Двойная оплата или подтверждение уже отменённого заказа могут привести к `REFUND_PENDING`, а не к автоматическому выполнению. Поздние PENDING/CANCELED не отменяют уже CONFIRMED. Повторное нажатие «Оплатить» при активной попытке возвращает сохранённую ссылку. После неопределённого результата `UNKNOWN`/`CREATING` новая оплата блокируется до выяснения.

После обычного подтверждения создаётся внутреннее событие для уведомления оператора в Telegram, отправка email покупателю выполняется по возможности. Эти каналы относятся к GSPro; получение Telegram/email не является источником доказательства оплаты. Автоматического пополнения игры модуль Platega не делает: заказ исполняет оператор.

## 7. Деньги списались, а заказ ожидает оплату

Не оплачивайте этот же заказ повторно. Найдите операцию в кабинете Platega по номеру заказа/описанию, сумме и времени. Запишите UUID транзакции (не сокращённый ID магазина, не банковский номер чека). Проверьте состояние платежа у провайдера.

После сохранения Callback URL нажмите **«Проверить оплату»** в заказе GSPro. Эта кнопка использует серверную сверку через `GET /transaction/{id}` независимо от callback. При ошибке сверки интерфейс сообщает: «Не удалось подтвердить оплату. Если деньги списались, не оплачивайте повторно и обратитесь в поддержку». [Проверка статуса Platega](https://docs.platega.io/проверка-статуса-оплаты-платежа-29203844e0).

На VPS доступна точечная сверка. Она читает Platega, затем **обновляет заказ по проверенному результату** и может запустить обычное уведомление оператора:

```bash
cd /opt/gspro
# Заменить UUID_ТРАНЗАКЦИИ действительным UUID из кабинета Platega:
./deploy/dc exec -T web node scripts/platega-reconcile.mjs UUID_ТРАНЗАКЦИИ
```

Ожидаемый вывод — `Transaction verified and reconciled.` После этого проверить заказ; при ещё PENDING он обоснованно останется неоплаченным. При отсутствии `transactionId` автоматический обход его не найдёт: UUID ищут у Platega, а скрипт восстанавливает связь через `payload`. Если попытка или заказ потеряны после восстановления БД, нужен отдельный разбор, а не ручная подмена статуса.

Автоматическая сверка использует `gspro-platega-reconcile.timer`. Фактическое расписание и активность проверяйте по действующим units. За проход проверяются подходящие попытки с известным UUID; наличие таймера не подтверждает успех каждой оплаты. Проверить состояние и последние результаты:

```bash
systemctl status gspro-platega-reconcile.timer --no-pager
systemctl status gspro-platega-reconcile.service --no-pager
journalctl -u gspro-platega-reconcile.service -n 40 --no-pager
cd /opt/gspro
./deploy/dc logs --since 30m --tail 100 web
```

`inactive (dead)` у успешно завершившегося oneshot-service нормально; таймер должен быть active. `checked:0` означает отсутствие подходящих попыток, а не доказанную оплату всех заказов. `failed>0` / `reconcile_failed` требуют диагностики. Ручной запуск всей сверки: `systemctl start gspro-platega-reconcile.service` — он тоже может менять статусы по ответам провайдера. Если units отсутствуют или таймер отключён, их установку/включение согласуйте отдельно как изменение системных служб; пустой callback этим не исправляется.

При диагностике исходящего GET записывайте HTTP-код и безопасные признаки формата ответа, не ключи, платёжные ссылки и полное тело с данными клиента. Разделяйте: DNS/TLS/таймаут; HTTP 401/403 (ключи/права); HTTP 404 (транзакция/мерчант); HTTP 429/5xx (ограничение/ошибка провайдера); HTTP 200 с ошибкой разбора (сопоставить фактические поля с `fetchPlategaTransaction`); ошибку применения в БД. Не считайте 404 доказательством отсутствия списания.

Для обращения в поддержку Platega подготовьте номер заказа, UUID, сумму/валюту, время с часовым поясом, Callback URL, статус кабинета, HTTP-код и обезличенную ошибку. Запросите историю доставок callback с HTTP-ответами и возможность повторной доставки. Secret не отправляйте.

### Комиссия Platega и отдельные суммы

Цена заказа GSPro не увеличивается при сверке. Допускается один из двух вариантов:

1. Сумма API точно равна сумме сохранённого заказа; дополнительная комиссия покупателя — 0.
2. Сумма API больше суммы заказа, API сообщает положительное поле `comission`, и **сумма API − comission = сумма заказа** до копейки.

Процент комиссии не задан в коде: он может зависеть от способа оплаты у Platega. Код не разрешает произвольную переплату, недоплату или несовпадающую комиссию. Вычитание допускается только из ответа авторизованного GET после проверки MerchantId, UUID и `payload`. Поля `comissionType`, `comissionUsdt` и `amountUsdt` не используются для угадывания курса или размера комиссии. Для другого недокументированного формата сумм проверка остановится и потребуется отдельный разбор.

В `PaymentEvent.rawJson` сохраняются отдельно `orderAmountKopecks`, `providerAmountKopecks`, `payerFeeKopecks`, `commissionKopecks` и валюта. `Order.totalAmountKopecks` и `PaymentAttempt.amountKopecks` остаются исходной ценой заказа. При оплате с комиссией в кабинете и на странице результата показываются стоимость заказа, комиссия Platega и оплаченная общая сумма. До перехода на оплату покупатель видит пояснение, что точная комиссия выбранного способа будет показана на стороне Platega.

## 8. Приёмка подключения

После согласования реального контрольного платежа проверить всю цепочку: заказ и сумма → ссылка Platega → успешная операция провайдера → callback HTTP 200 → заказ «В работе» → уведомление оператора → выполнение. Отдельно проверить серверную сверку; успешный GET не доказывает работоспособность callback. При повторной доставке не должно появляться повторное выполнение.

Наличие публичного sandbox этим документом не предполагается. Тестовый merchant, адрес API, ключи и правила операций без реального списания нужно получить у Platega. Имитация API в локальных тестах проверяет код, но не реальный магазин, банки или доставку callback. Страница «Run in Apidog» не гарантирует отсутствие реального движения денег.

## 9. Возвраты, отключение и восстановление

В GSPro не реализованы вызовы API возвратов, выплаты на карты, чтение баланса, рекуррентные подписки и экспорт транзакций Platega. Они не требуются для этой интеграции общей платёжной страницы. Возврат выполняется ответственным через согласованный процесс провайдера; статус «Возвращён» в GSPro сам деньги не отправляет. Зафиксируйте подтверждение возврата и отдельно обработайте заказ, как указано в `14_Сверить_платёж_и_оформить_возврат.md`.

Для закрытия новых продаж выключите «Приём платежей на сайте» в админке и подтвердите действие 2FA. Требуется право `checkout.write`; изменение `TechnicalSettings.checkoutEnabled` фиксируется в аудите. Сохраняйте `DEPLOY_MODE=production`, действующие ключи и HTTPS-адрес. Второй комплект приложения, пересборка и смена тегов не нужны.

Выключение блокирует новые платные заказы и создание платёжных ссылок. Аутентифицированные callback и API-сверка существующих транзакций продолжаются. Уже выданные ссылки у провайдера не отменяются автоматически; отключение не означает отмену списаний. Заказ с полной скидкой может пройти без оплаты. Проверьте галочку и поведение нового оформления, затем разберите незавершённые операции.

После восстановления БД сверяйте операции Platega за период после снимка; возврат базы к прошлому состоянию не отменяет банковских операций. После смены домена обновите callback; после ротации ключа примените окружение контейнеров и проверьте оба направления. Не восстанавливайте устаревший секрет поверх нового без проверки.

## 10. Карта реализации и источники

- `app/lib/platega-config.js`: включение, секреты, домен, API URL, таймаут, разрешённый хост оплаты.
- `app/lib/platega.js`: создание ссылки, GET статуса, разбор и аутентификация событий.
- `app/lib/platega-service.js`: PaymentAttempt, повторы и переходы статусов.
- `app/lib/platega-amounts.js`: точная сверка стоимости заказа/комиссии и безопасное представление квитанции.
- `app/app/api/payments/platega/callback/route.js`: входящий POST и HTTP-ответы.
- `app/app/api/payments/status/route.js`: кнопка «Проверить оплату».
- `app/scripts/platega-reconcile.mjs`: ручная и фоновая сверка.
- `/etc/systemd/system/gspro-platega-reconcile.{service,timer}`: расписание и запуск существующей службы.
- `deploy/dc`, Compose, `deploy/Caddyfile`: окружение и маршрутизация.
- [Официальный индекс Platega](https://docs.platega.io/llms.txt); профильные страницы связаны выше.

После восстановления используйте [актуальный порядок нового VPS](../Восстановление/01_На_новый_VPS.md) и сверяйте состояние приёма платежей до открытия сайта. Инструкция не является подтверждением выполненного контрольного платежа.
