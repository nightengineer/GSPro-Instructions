# Архитектура и потоки данных

## Заказ

1. Браузер получает одноразовый CSRF-токен.
2. `/api/orders` повторно загружает игру и серверный курс, проверяет лимиты, email, UID и четыре независимых обязательных подтверждения.
3. UID шифруется AES-256-GCM; для антифрода сохраняется HMAC-отпечаток. Открытый UID не участвует в поиске.
4. PostgreSQL создаёт заказ, номер, случайный `payload` и отдельные записи Consent.
5. После коммита сервер создаёт ссылку Platega и сохраняет её только если заказ всё ещё ожидает оплату.
6. Callback проверяет секреты, сохраняет уникальное событие и ищет заказ по transaction ID либо `payload`.
7. Обновление статуса выполняется условным `updateMany`; оплаченный заказ нельзя понизить событием FAILED. Уведомление отправляется только при реальном переходе в PAID.

## Доступ к UID

Обычные API кабинета и списка администратора UID не возвращают. Отдельный Route Handler проверяет действующую роль в БД, CSRF и причину, пишет AdminAudit и только затем расшифровывает значение. Клиент удаляет его из состояния через 60 секунд.

## Деградация

Витрина может показывать fallback-каталог без БД. Любая операция, меняющая данные, при отсутствии PostgreSQL возвращает 503; в памяти заказ или согласие не создаются. Это исключает ложное впечатление о принятом заказе.
